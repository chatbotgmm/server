# 진행 보상·환생 API (검토용, 운영 적용 전)

## 인증과 요청
기존 `/my/api/native/` 세션 인증과 CSRF guard, 사용자별 native 직렬화 및 GameService SQLite 트랜잭션을 사용한다. 신규 HTTP API는 클라이언트 점수/등급/보상/시각/능력치 입력을 받지 않는다.

- `GET progression`: 서버 상태와 개체별 후보 반환
- `POST progression/pass/claim`: `{requestId,milestoneId}`
- `POST progression/reroll/claim`: `{requestId}`
- `POST progression/reincarnate`, `POST progression/reassess`: `{requestId,key:"o123"}`
- `requestId`: 8~80자의 영숫자/밑줄/콜론/하이픈. 같은 사용자·키·작업·payload 재요청은 영속 영수증을 그대로 반환한다. 같은 키의 다른 요청은 거절한다.
- 성공: `{ok:true,...결과}`. 확정 입력/자격 거절: HTTP400 `{ok:false,retryable:false,error}`. HTTP401도 같은 확정 표시. 500/연결 실패 후에는 같은 요청 키로 재시도한다.
- 시각은 전부 epoch milliseconds, 이력 없는 시각은 null. 서버 시각 기준이다.

## 아직 사용자 확정값이 아닌 기본 밸런스
- 환생: 최상위 **개체 하나**를 소모하여 기존 일반 종 중 하나를 균등 선택. +N은 누적되고 최초 계보의 고유기 한 슬롯만 보존한다. +5 전용 신규 기술은 구현하지 않았다.
- `PROGRESSION_REBIRTH_BONUS_PCT`: 단계당 5%, 허용 1~25. 총 능력치 보너스는 25% 상한. 보너스는 개체에 저장하므로 기존 개체는 설정 변경으로 소급 변경되지 않는다.
- 일반~전설 계보에는 기존 조상의 전투 정의/속성/직무를 내부 계산에 사용하고, 화면의 이름·id·썸네일은 실제 일반 종을 사용한다. 일반~전설 전투 전용 그림이 없으면 `/thumbs/실제종.jpg` 정본을 반환한다. 능력치는  직무 기본 능력치×일반 배율1×저장된 보너스를 적용한다. 최상위로 조합 성장하면 새 최상위 종의 본래 능력치에 같은 보너스를 적용한다. 새 캐릭터/그림은 만들지 않는다. 처음 성장 레벨은 기존 story.start.level(현재5)을 따른다.
- 고급 모집 희귀/전설 재심사: 동일 등급의 다른 종 중 균등 선택. `PROGRESSION_REASSESS_HOURS` 기본24시간(1~720). 무료이며 점수/첫 획득 재화/천장 진행을 추가 지급하지 않는다.
- 플레이 포인트: 성공한 모집1회/탐험 정산1회당1, 조합1회당3, 스토리·실시간 전투 승리당3. 항복/중단/연습 승리는0. `PROGRESSION_DAILY_CAP` 기본100(1~1000), 한국 날짜 기준. 10/30/60/100 누적점수에서 뽑기권1/3/5/10장. 시즌/결제/광고SDK 없음.
- 추가 리롤: 수령 간격5시간, 수령 후30분 이내에 기존 리롤을 사용한 제안 칸을 **한 번 더** 변경. 중첩되지 않는다. 무료 기본 칸 리롤은 그대로 유지된다.

## 개체와 계보 안전성
보호/탐험/전투·매칭 중 개체는 환생·재심사할 수 없다. SQLite 조건부 소비와 결과 지급/도감/영수증은 한 트랜잭션이다. 조합 한 결과당 계보 한 개만 승계하고, 두 계보가 충돌하면 전부 취소한다. 묶음 조합은 각 결과별 재료 그룹에 대응해 계보를 승계한다. 판매/땅콩떼기로 계보를 없애는 요청은 명시적으로 거절한다. 조합 중에도 활성 실시간 상태를 확인한다.

고유기는 교체할 수 없는 한 슬롯으로 유지한다. 개체 번호로 성장·실시간 준비·실시간 전투 경계를 검증하므로 같은 종의 일반 개체에 능력이 새지 않는다. 일반/랭크 모두 계보 메타데이터를 DB에서 읽고, 클라이언트 저장 JSON의 능력치/계보 입력을 신뢰하지 않는다. 랭크 레벨/승진 정규화 규칙은 유지된다.

새 고급 모집부터 `obtainedVia=GACHA_HIGH`를 기록한다. 과거 `GACHA` 기록만으로는 고급 여부를 증명할 수 없어 자동 소급 허용하지 않는다. 계보 조합 결과는 재심사 대상이 아니다.

## 리롤 범위 및 기존 구조의 한계
스토리/연습과 영속 실시간 normal/rank에서 추가 리롤을 지원한다. 구식 리플레이 기반 native normal 경로에서는 보너스 사용을 차감 전에 거절한다. 기본 리롤은 여전히 가능하다. 추가 리롤 상태는 전투 응답 `bonusReroll.available/expiresAt`로 전달한다. Android는 사용 완료된 칸이라도 유효한 보너스가 있으면 클릭 가능하게 해야 한다.

실시간 전투는 전투 JSON·보너스 차감·요청영수증이 동일 DB 트랜잭션이다. 기존 스토리/연습 전투 자체는 서버 메모리에만 존재한다. 보너스 차감 영수증은 영속적이지만 서버 종료 시 스토리 전투 복원은 기존 엔진이 지원하지 않는다. 운영 적용 전에 이 기존 복원 한계를 수용하거나 별도 영속 전투 저장 작업이 필요하다.

## 적용 및 검증
`prisma/manual/20261019_progression_additive.sql`은 수동 검토용 추가 SQL이다. 운영에 실행하지 않았다. 운영 적용은 백업·동일 스키마 확인·별도 승인 후 한 번만 해야 한다. 코드 배포 전에 스키마 적용/Prisma client 재생성이 필요하다.

격리 CI: Node22+, `npm ci`, `npx prisma generate`, `npm run test:db`, `npm run build`. `test:db`는 새 `/tmp/galmaegiman-tests-*` SQLite를 만들고 seed 후 모든 테스트를 실행한다. 운영 연결정보가 필요 없다. 신규 `test/progression.integration.test.ts`는 별도의 임시 SQLite를 만들고 지운다.

### 운영 호환성 / 되돌리기
서버 기동은 `assertProgressionSchema`로 새 열·테이블을 읽기 검사하고 누락 시 listen 전에 중단한다. 따라서 미적용 DB에 기능만 노출되는 상태를 허용하지 않으며, 자동 마이그레이션은 없다. 신규 코드와 이전 DB를 섞어 서비스하면 안 된다.

승인된 적용 시에는 트래픽을 멈추고 SQLite의 일관된 백업(`.backup` 또는 기존 공식 backup 스크립트)을 보관한다. 작업 DB 복사본에 추가 SQL을 적용하여 기존 OwnedCharacter 행·Player 잔액이 그대로이고 신규 필드 기본값이 0/null인지 먼저 확인한다. 그 후 승인된 운영 적용, Prisma client 생성, 테스트 완료 코드를 함께 시작한다. 이 작업에서는 운영 단계를 실행하지 않았다.

코드만 이전 버전으로 되돌리는 것은 안전한 롤백이 아니다. 이전 버전은 계보를 모르므로 조합/판매에서 계보를 잃을 수 있다. 신규 기능으로 쓰기가 발생하기 전에는 서버 중지 후 백업 DB+기존 코드 세트를 복원할 수 있다. 쓰기가 발생한 뒤에는 영수증·소모·보상 자료를 보존하고 복원 계획을 별도 검토해야 한다. 신규 열/테이블 DROP 또는 영수증 삭제는 롤백 수단으로 사용하지 않는다.
