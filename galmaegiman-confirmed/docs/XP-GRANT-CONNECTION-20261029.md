# 개체 XP 지급 연결 점검과 새 전투 한정 수정

기준 커밋은 `60d5ddea0d2754f19ce8dc7db105d307a7fe4d60`이다. 운영 서버·운영 DB·설치 APK를 검사하거나 과거 보상을 소급 지급하지 않았다. 이번 제품 변경은 `src/story/service.ts`에 한정하며, 보상량·성장 곡선·전투 수식·스키마·클라이언트 제품 코드는 바꾸지 않는다.

## 확인한 원인과 수정 경계

기존 서버는 의뢰 수락 시 `accepted[questId].unitXpPolicy`를 저장한다. 정책을 사용할 수 없던 시점의 `null` 또는 구형 저장 데이터의 누락 필드도 계속 고정돼, 이후 정책이 활성화돼도 해당 의뢰의 새 전투가 XP 0 계약을 물려받았다. 이는 코드와 격리 DB에서 확인한 경로이며, 사용자의 실제 계정이 이 상태였다는 운영 증거는 없다.

새 출항 예약 트랜잭션에서만 정책이 없는 ACTIVE 의뢰에 현재 검증된 기존 정책을 한 번 연결한다. 기존 non-null 정책은 금액과 버전을 유지한다. 현재 정책도 없으면 새 양을 만들어 지급하지 않는다. 잘못된 정책은 503 `STORY_UNIT_XP_POLICY_INVALID`로 거절하고 예약·정책·보상 변경을 롤백한다. 요구 승리를 이미 채운 미귀환 의뢰는 `STORY_OBJECTIVE_AWAITING_RETURN`으로 추가 전투를 막는다.

완료된 출항 영수증과 내부 전투 생성 영수증을 먼저 복구하고, ACTIVE/FINISHED 스토리 전투가 있으면 새 출항을 차단한 뒤 정책을 연결한다. 따라서 진행 중 전투·이미 끝난 전투·정산한 전투의 스냅샷과 영수증은 XP 0을 포함해 바뀌지 않는다. 아직 전투 스냅샷이 없는 pending 출항은 재시도 때 새 정책을 받을 수 있다. 예약 후 모험 연결이나 전투 생성이 실패해도 예약과 함께 고정한 정책은 남고, 재접속은 같은 출항·모험을 재사용한다.

## 실제 지급 경로

| 진입 경로 | 개체 XP 대상과 시점 | 현재 패배·도주 처리 |
| --- | --- | --- |
| 일반 PvP 및 일반전 AI | 실제 출전한 ownedId끼리 고정 XP 풀 분배. 승리 100%, 패배 50%. 종료 트랜잭션에서 개체 XP·ledger·정산을 함께 저장 | 패배 50%, 항복/도주 0 |
| 정책 있는 직접 스토리 | 실제 출전 ownedId에 해당 전투의 서버 정책 금액을 균등 분배. 전투 정산에서 저장 | 현재 스토리 정책은 패배·도주·무승부 0 |
| 정책 있는 모험형 스토리 | 실제 출전 ownedId 몫을 run에 보관. 정상 귀환 트랜잭션에서 실제 개체 XP에 저장 | 전멸 시 미정산 XP 폐기. 성공한 도주는 새 XP 0, 앞선 승리분은 귀환 가능 |
| 독립 일반 모험 | 서버 조우의 기존 승리 XP를 출전 개체 100%, 미출전 예비 50%씩 보관. 정상 귀환 때 지급 | 전멸 시 run 미정산 XP 폐기. 도주 자체는 0 |
| 기존 단일 PvE 연습전 | 전투 시작 시 최초 ownedId 하나에 기존 encounter.winXp/lossXp 지급 | 기존 lossXp 사용. 예비 개체에게 지급 대상을 확대하지 않음 |
| 스토리의 독립 흑화 재료 모험 | accepted-quest 정책 대상이 아니며 원본 encounter.winXp는 0 | 기존 0 계약 유지 |
| 랭크 | 현재 일반전 XP 정책 범위 밖으로 개체/계정 XP 0 | 기존 계약 유지 |

금액과 정책은 클라이언트 요청 값을 신뢰하지 않는다. 개체의 `Roster60Owned.totalXp`와 개체 소유자·상태·시작 XP를 대조해 저장하며, 같은 종이라도 ownedId가 다른 개체를 합치지 않는다. 같은 요청과 같은 전투의 다른 requestId 재조회는 지급을 반복하지 않는다. 정상 귀환 전 보관 XP는 성장 레벨에 미리 적용하지 않는다.

계정 XP는 `CommanderAccount`/`CommanderXpLedger`의 별도 사건이다. 스토리는 전투마다가 아니라 의뢰 완료 때 계정 XP를 지급하고, 연결 모험의 귀환으로 계정 XP를 한 번 더 지급하지 않는다. 계정 XP가 정상이라고 개체 XP 지급을 판정하지 않았다.

개체의 기존 60/99 상한, 넘친 XP 폐기, 자동 환생 없음은 변경하지 않았다. 같은 종 3개체의 실제 지급 시험은 기존 설정 `STORY_01_01` 승리 XP 1695를 출전 2개체에 847/848로 나눴고, 미출전 예비와 다른 계정은 그대로였다. 두 수령 개체는 XP가 증가해도 다음 레벨 문턱에 못 미쳐 Lv15를 유지했다. 이 값은 선택된 시험 프로필의 실제 금액이며 운영 보상 승인이나 전체 캠페인 완주 증거가 아니다.

## API와 표시 점검

직접 스토리의 기존 정산 DTO는 `xpAwarded`에 실제 합계와 `unitXp.units[].appliedXp`/`xpProgress`를 함께 보낸다. 현재 일반 결과 문구가 legacy 필드를 읽어서 modern 지급을 +0으로 보인다는 가설은 이 DTO에서는 재현되지 않았다. 모험의 `xpAwarded: 0`/`xpEscrowed`와 `delivery: pending-return`은 보관 상태이고, 실제 지급은 귀환 응답의 `settlement.rewards.xp`/`xpProgressByOwnedId`이다.

현재 클라이언트는 FINISHED → settle 호출에 부착된 View를 사용하고, 정산 receipt가 없던 FINISHED 응답이 이후 XP 영수증 표시를 차단하지 않는다. 별도 클라이언트 점검은 동일 레벨에서 부분 XP 증가, 같은 종 다른 ownedId, 늦은 응답 무시, 새로고침·화면 복귀·재열기를 검증했다. 클라이언트 제품 코드 수정은 없다.

## 적용과 남은 결정

이 작은 연결 수정은 서버 소스 반영이 필요하다. API·스키마가 바뀌지 않아 신규 마이그레이션이나 새 앱 기능은 요구하지 않는다. 기준 60d5 이후 변경은 보존해 내용 병합하고, 운영 반영 전 대상 서버가 실제 사용하는 프로필과 정책 파일을 확인해야 한다. `storyUnitXpPolicyReader`는 현재 `ROSTER60_PROFILE=five-stat-device-test-v1`에서만 기존 정책 파일을 읽는다. 정책 부재에 대한 운영 기본 금액을 이번에 새로 추가하지 않았다. 설치 APK의 버전·커밋과 운영 환경 설정은 미확인이다.

스토리/모험의 현재 패배 0 및 전멸 시 XP 폐기는 사용자의 “패배도 XP” 요구와 충돌한다. 일반전의 50%를 다른 모드에 자동 이식하지 않았으며 해당 비율과 모험의 실패 지급 시점은 결정이 필요하다. 독립 흑화 재료 모험의 0 XP도 이 패치로 새 양을 정의하지 않는다. 과거 정산의 소급 지급, 자동 환생, 서버 배포·푸시·운영 DB 수정은 수행하지 않았다.

## 검증 기록

선택한 격리 DB 회귀의 정확한 파일 수·시험 수·명령과 소스 해시는 인계 묶음의 `VERIFICATION.txt`, `forward-final-reproduction.json`, `forward-final-vitest-summary.json`에 기록한다. Android의 별도 5개 시험은 같은 개체 캐시/표시 회귀이며 서버 시험 수에 합산하지 않는다. 실제 사용자 계정 지급·설치 APK·실기기 FPS·전 캠페인 완주는 검증 범위 밖이다.
